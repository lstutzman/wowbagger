The HTML report is a static snapshot: state counts, item cards, a terminal table, swarm batches. Counts-by-state are vanity metrics; the report answers "what exists" but not the question it is for. Its purpose is: **show what needs to be worked, in order, and why** - by user ask, by security exposure, by what enables other large items. Research: `docs/research/2026-08-15-useful-backlog-reports.md` (Part 1 flow/health canon, Part 2 sequencing canon and the wowbagger mapping).

Design constraints (from the research):

- The core never invents or recalculates priority; `ready` stays the deterministic queue (priority, created, id). The recommended order is a **report-layer derivation** - explainable, never persisted, never a mutation, no `ready` contract change.
- Ordering factors are **shown, not hidden in one opaque score**. The reasons are the report.
- Value dimensions (user ask, security, fixed date) ride the existing extension-field + report `fields` mapping mechanism (like `area`/`complexity`): a documented `class` convention (`expedite|fixed-date|standard|intangible`) plus optional `due`. No new core fields.
- Structural factors are computable today from the ledger alone: transitive unblocking leverage over the `depends_on` DAG (reverse edges), epic enablement from `parent` (siblings terminal/total), age from `created`, and `complexity` as a WSJF-style size denominator where present.

Report shape (top to bottom):

1. **Work next** - ranked ready items, each entry carrying its reasons, e.g. "#38 - unblocks epic #21 (85% done) - age 12d" or "#77 - expedite/security - age 30d". Rank dominance: expedite class, fixed-date proximity, unblocking leverage, epic enablement, priority, age tiebreak.
2. **Attention** - oldest aging open items, blocked items naming their blockers, in-progress/claimed items past the historical p85 age.
3. **Evidence layer** - throughput/week, arrivals vs completions, aging buckets, cycle time (accept-to-complete) median/p85, Monte Carlo forecast band for remaining open work. All derivable from per-item `created`/terminal dates and decision records; no snapshot storage.
4. Existing cards and swarm batches demoted to drill-down; the machine JSON model keeps serving agents.

Acceptance criteria:

- The report opens with the ranked work-next list; every entry shows number, title, and its ranking reasons; the ranking is deterministic for a given ledger and as-of date.
- Unblocking leverage is transitive and correct on a diamond-shaped dependency graph (mutation-guarded test).
- Epic enablement names the parent epic and its terminal-children ratio.
- A `class: expedite` extension field lifts an item to the top band and renders the class label; absent class means standard; unknown class values are reported, not silently dropped.
- Attention list flags blocked items with blocker numbers and aging items with their age.
- Evidence layer renders throughput, aging buckets, and a probabilistic forecast (50/85 percent bands) from the current ledger bytes alone.
- Ranking logic lives in the report layer; `ready --json` output and the mutation contract are byte-for-byte unchanged (regression-tested).
- Items are referred to by number (#N) everywhere in the rendered report; ULIDs appear only in drill-down detail.
- Four-command gate green on both Node runtimes; report fixtures regenerated; mutation-guard each new ranking rule (break it, watch the test go red).
