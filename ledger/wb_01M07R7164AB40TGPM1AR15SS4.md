Observation from PropertyCompass2 (2026-08-17), accepted as fair: this repository's own ledger keeps items at the root with no .wowbagger/layout.json - the documented default, not a bug, but it means the layout binding shipped without being dogfooded, which is plausibly why the consumer's misplacement family (#94/#102/#104) took three cycles and a git mv workaround to surface. The two mirror gaps (#114/#116) share the shape: what happens to a consumer whose ledger is not a pure copy of something else is under-exercised because our own ledger is the simplest possible case.

Scope: adopt the layout binding on this repository's own ledger.
1. Add ledger/.wowbagger/layout.json ({"layout_version":1,"items_directory":"items"}) and git mv all item files into ledger/items/ in ONE commit - committing the layout with items still at the root makes the ledger invalid (item-outside-layout, by design, per #104).
2. Run the full loop afterwards on the real ledger: validate, ready, inspect by number, one create (lands in items/), one transition, claim-verify - all green.
3. Anything that hardcodes root-relative item paths (report config, tests reading ledger/*.md paths, the handoff docs, helper scripts) gets swept; the #104 remediation strings are the recovery if the migration commit is mis-staged.
4. Record in the closing decision what the dogfood surfaced, if anything - that record is the point.

Acceptance:
- This ledger's items live under items/ with the layout committed; every core command green against it; the ledger stays valid at every commit boundary.
- A create lands in items/ (proven once, then reverted or kept as a real item).
- Gate green on both runtimes.
