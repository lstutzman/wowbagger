# Items 165–172 reconciliation and auto-commit design

## Goal

Fix actual ledger items #165–#172 as one coherent reconciliation and auto-commit change. Preserve fail-closed handling for genuine unauthorized edits, preserve honest `state: committed` responses, and keep unrelated worktree activity from blocking or falsely failing a target mutation.

## Scope

This design covers:

- #165: classify an uncommitted, in-protocol sibling revision as synchronization-required without weakening unauthorized-edit detection.
- #166: document the effective terminal-item date equality constraint for patch, snooze, and parent migration.
- #167: remove the false `live` restriction from parent-migrate help.
- #168: document parent-migrate and snooze request, response, and journal fence-family semantics.
- #169: recover in protocol when prior claim evidence dirties the derived reconciliation log.
- #170: preserve claim-verification refusal diagnostics after a commit lands.
- #171: define useful retryability for cross-worktree claim-store contention.
- #172: align preflight and post-commit finding scopes.

No release cut, npm publication, core contract-version bump, or unrelated refactor is included.

## Architecture decisions

### Target-scoped reconciliation end to end

Preflight and post-commit verification use the same target-scoping rule. An unrelated `worktree-synchronization-required` finding does not fail the target mutation. A finding for the target item, or any finding classified as globally blocking, still fails.

A successful auto-commit keeps its current envelope. `claim_verified: true` means the ledger is valid and no finding blocks the target item. Nonblocking findings remain internal to the verification step; no success-envelope member is added.

The mutation contract changes from “no findings” to “no blocking findings.” This preserves unrelated-worktree concurrency and avoids making #165 trade a false pre-write refusal for a post-write reported failure.

### Safe sibling-revision classification

The reconciliation loop already computes `authorizedRevisions`, including predecessor revisions named by legacy mutation intents. Thread that set into `reconciliationDiagnosis`.

When all of these are true:

- actual bytes differ from the latest authorized revision,
- actual bytes equal a revision previously authorized for that item,
- the latest authorized revision is not yet attributable to a reachable Git ref,

classify the state as `worktree-synchronization-required`. This is a legitimate stale sibling view, not an unauthorized edit.

If actual bytes are not in `authorizedRevisions`, retain `unauthorized-revision`. Do not relax the existing file-present guard without this discriminator; doing so would turn genuine hand edits into nonblocking findings.

Committed sibling revisions continue to report `owner_ref` and `owner_commit` through existing Git ownership evidence.

### Derived reconciliation-log recovery

The authoritative claim journal remains the source of truth. The tracked reconciliation log remains derived.

For journal-owning auto-commit commands, the initial cleanliness check may tolerate exactly the current namespace reconciliation-log path. Internal claim verification rebuilds that file from the authoritative journal before the commit set is prepared. The later cleanliness check already permits the command-owned log.

Every other staged, tracked, untracked, or partially staged ledger path still refuses. `create` remains strict because it does not own or commit the reconciliation log. Claim refusal evidence continues to be persisted and projected; this change must not suppress journal or projected-log writes.

### Refusal diagnostics and retryability

When internal claim verification refuses, preserve these optional diagnostic members:

- `claim_verify_code`
- `claim_verify_reason`
- bounded `findings`

Preflight `claim-state-unreconciled` sets `retryable: true` only when `claim_verify_reason` is `claim-store-locked`. Persistent publication reconciliation, invalid journals, and other non-mutex causes remain non-retryable.

Post-commit `post-commit-reconciliation-failed` carries the same diagnostic members. It does not read findings from a nonexistent success `result`, and it does not invent `findings: []` when the refusal supplied no findings.

`state: committed`, `git_commit`, `published_revision`, and `commit_paths` remain authoritative. Callers never replay the mutation merely because `ok` is false.

The per-working-tree auto-commit mutex remains unchanged. Cross-worktree parallelism is preserved; the underlying claim-store reason provides the retry signal.

### API compatibility

No root envelope, response domain, command name, required member, or schema-fixed auto-commit detail changes. New diagnostic members are optional and extend existing error details. Existing members retain their meanings.

Core `contract_version` remains 5. The semantic fixes are documented in the current contract and changelog-ready Unreleased section; a later distribution cut moves the version pin separately.

## Documentation behavior

### Terminal-item dates

The whole-ledger invariant requires the active lifecycle date (`completed`, `killed`, `archived`, or `deferred`) to equal `updated`. Patch, snooze, and parent-migrate set `updated` from request `date` without changing the active lifecycle date. Their date floor rejects earlier dates. Therefore a lifecycle-dated item accepts these verbs only when request `date` equals its existing `updated`.

Document this derived equality for all three verbs and all four affected statuses. Keep the current `candidate-invalid` channel and whole-ledger invariant.

### Parent-migrate help

Replace “Move one live item to or from an epic with CAS fencing.” with wording that does not invent a status restriction. The implementation correctly permits any item whose request satisfies date, revision, parent CAS, self-parent, and epic-kind checks. Do not add a liveness guard.

The help must cross-reference the terminal-date constraint conceptually: historical items are supported, but their request date is fixed to current `updated`.

### Parent-migrate and snooze contract sections

Add dedicated sections defining:

- exact request JSON members,
- revision and parent compare-and-swap rules,
- date behavior including terminal equality,
- response domains and exit classes,
- auto-commit behavior,
- durable journal semantics.

The journal `command` member records a legacy fence family or recovery classifier. `responseCommand` identifies the public response operation. Parent migration and snooze use the `patch-v1` fence family while returning `parent-migrate-v1` and `snooze-v1` ledger-mutation envelopes. This is intentional and must not trigger a journal-format rewrite.

## Error handling invariants

- Genuine unauthorized file-present bytes remain blocking.
- A target-item finding remains blocking even when its reason is synchronization-required.
- Invalid ledger state still fails post-commit verification.
- Claimed publication still requires its finalization row to name the created Git commit.
- Dirty foreign ledger paths never enter an auto-commit set.
- Refused claim operations continue to persist authoritative time and evidence.
- A committed mutation never becomes safe to replay because verification failed.

## TDD sequence

Each behavior uses one RED-GREEN-REFACTOR cycle before the next behavior begins.

1. #165: write a two-worktree failing regression for the uncommitted sibling predecessor; add a companion regression proving unknown bytes remain unauthorized; implement the smallest classifier data-flow change.
2. #169: write a failing claim-decision-to-auto-commit regression; add guards for foreign dirt and create; implement the initial preflight log allowance and rebuild path.
3. #170: write failing post-commit refusal tests with and without findings; preserve code, reason, and findings minimally.
4. #171: write failing retryability tests for `claim-store-locked` and persistent reconciliation; add optional underlying reason and override retryability only for the lock case.
5. #172: write a failing post-commit test with an unrelated synchronization finding and a companion target-finding failure; align the post-commit check with target scoping.
6. #166–#168: write failing documentation/help assertions first, then update help and contracts.

Every RED must fail for the missing behavior, not for syntax or fixture setup. Every GREEN runs the complete relevant test file, not only the new test case. Refactoring happens only after GREEN.
