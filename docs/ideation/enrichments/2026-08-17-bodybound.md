## 1. Current reality

- Baseline: repository `HEAD` is `cd4b27d4fe5a051366ef6d5ba45223366d86b031`; `package.json` is `0.1.0-alpha.6`. The relevant files have no diff from local tag `v0.1.0-alpha.6` (`26369efffb36a2a2a393671437ddfa05f154b623`).
- `publish-claimed` has two exact limits. `src/claim-publication.js:24-25` defines `MAX_CANDIDATE_BYTES = 8,388,608` and `MAX_CANDIDATE_BASE64_CHARS = 11,184,812`. `validatePublicationRequest` rejects a longer base64 string before decoding and rejects decoded bytes above 8,388,608 (`src/claim-publication.js:37-75`). `src/cli.js:61,390-448` separately caps the complete serialized request at `11 * 1024 * 1024 = 11,534,336` bytes. The contract pins both values at `docs/work-claim-contract.md:627-635`.
- The skeptic's “named size error” premise is wrong. There is no size-specific error. An over-8-MiB decoded candidate is folded into exit 2 `invalid-request`, state `unchanged`, message `The candidate source is not canonical base64.`, and `details.field: "candidate_source_base64"` (`src/claim-publication.js:63-75,1095-1099`; `docs/work-claim-contract.md:667-672`). A request over 11,534,336 bytes is also `invalid-request`, but with message `The request does not match publish-claimed version 1.` and `details.field: "input"` (`src/cli.js:419-426`). The former message falsely describes a canonical but oversized candidate.
- `create`: no request, body, or serialized item bound. `validateCreateRequest` checks only that `body` is a string (`src/mutation.js:124-144`). `createCandidateSource` encodes the complete serialized item without a size check (`src/mutation.js:2185-2189,2226-2265`).
- `patch`: no request, replacement-body, appended-body, or successor-item bound. `validatePatchRequest` checks only string type and replacement/append exclusivity (`src/mutation.js:775-855`). `buildPatch` and `serializePatch` build the complete successor without a size check (`src/mutation.js:876-900,1030-1066`).
- `transition`: it does not accept a body, but it can grow an item through unbounded decision strings. Its serialized successor has no bound (`src/mutation.js:448-517,1152-1184`). A unified item bound must cover it too, or it leaves a write door open.
- Direct CLI file and stdin transport are unbounded by the core. `requestSource(input, maxBytes = Infinity)` stats then reads a whole file, or accumulates every stdin chunk and calls `Buffer.concat`; create, transition, and patch call it without a finite argument (`src/cli.js:218-260,284-304,1350-1371`). `parseJsonRequest` then decodes the complete buffer and builds a complete value tree (`src/request.js:3-19,74-225`). Node/V8/OS memory and buffer ceilings are the eventual accidental limit [INFERRED], not a Wowbagger contract.
- The adapter is a separate, smaller door, not a core guarantee. Its complete invocation is capped at 65,536 bytes and stdout at 1,048,576 bytes (`src/adapter/entrypoint-main.js:20-26,319-325`). A direct CLI call bypasses that adapter limit.
- Observed on this checkout with a fresh `/tmp` ledger: a file request containing exactly 52,428,800 ASCII body bytes returned exit 0, `ok: true`, `state: committed`. Request size was 52,429,008 bytes; item size was 52,429,082 bytes; JSON output was 122,334,911 bytes because the success item contains both `body` and `source_base64` (`src/mutation.js:111-121`; `src/cli.js:840-847`). Runtime was 0.70 s. Thus alpha.6 accepts a 50-MiB create; behavior is not merely theoretical.
- Core capabilities already has `result.limits`, but it exposes only six coordination/atomicity booleans and no byte limit (`src/cli.js:617-668`; `docs/mutation-contract.md:479-580`).

## 2. Sharpened design

- Define one public semantic limit: `MAX_ITEM_SOURCE_BYTES = 8_388_608` (8 MiB), measured over the complete UTF-8 Markdown item source that revision hashing and `source_base64` already represent. Do not call it a body limit: frontmatter, decisions, extensions, and body all consume the budget.
- Rationale: 8 MiB is already published in work-claim version 1, so reusing it avoids two meanings of “publishable item.” It also gives the live consumer more than 100 times headroom over its largest item. A lower value would newly narrow `publish-claimed`; a higher value would weaken its existing resource boundary.
- Put the constant in one core limits module. `src/claim-publication.js`, mutation candidate builders, capabilities, tests, and independent oracles consume the value or independently pin the same contract value. Production code must not import either oracle.
- Add one semantic refusal at every candidate door: code `item-source-too-large`, message `The proposed item source exceeds the supported byte limit.`, exit 2, state `unchanged`. Core-domain details are exactly `{id, size_bytes, limit_bytes}`. Ledger-publication details are exactly `{item_id, size_bytes, limit_bytes}` and retain top-level `operation_id` after strict schema acceptance. Response roots and version lookup stay owned by their response domains (`docs/mutation-contract.md:260-352,394-435`).
- `create`: after schema version and number assignment, check `createCandidateSource(...).length` at `src/mutation.js:318-338`, before candidate-ledger validation, temporary-file creation, or publication.
- `patch` and `transition`: check the serialized `Buffer.length` returned by `buildPatch` / `buildTransition` before complete-ledger candidate validation and publication (`src/mutation.js:876-900,1152-1184`). This covers `body`, `body_append`, decision growth, and frontmatter-only growth.
- `publish-claimed`: keep the base64-character precheck to avoid decoding an impossible candidate, then return `item-source-too-large` when decoded length exceeds 8,388,608. Keep malformed base64 as the existing canonical-base64 `invalid-request`. Keep the 11,534,336-byte serialized-publication-request limit as a separate transport limit; it measures a different object.
- Do not make oversized stored items a `validate` error. Reads must remain available, and a patch that produces a successor at or below 8 MiB must be able to repair a legacy item. Any successor still above the limit refuses.
- Add `result.limits.max_item_source_bytes: 8388608` to core capabilities. It applies to successor bytes accepted by create, transition, patch, and publish-claimed. It does not claim a raw JSON request limit or an inspect-output limit.
- Version position: ship this as core `contract_version: 4`, with the next distribution release and an explicit compatibility note. Alpha status does not make a documented accepted-input narrowing compatible. It does not require npm `1.0.0`, but a release note without the core contract bump is insufficient.
- If the same new refusal must replace publish-claimed's pinned version-1 error, also bump `result.operations.work_claim.api_version` to 2. The accepted publication set does not narrow, but work-claim v1 pins the old code and message (`docs/work-claim-contract.md:660-672,891-908`). Keep the ledger-publication root `contract_version: 1` only if the response-domain doctrine continues to treat it as the legacy envelope marker; consumers negotiate the work-claim API field (`docs/mutation-contract.md:271-290`).

## 3. Hidden risks

1. **Compatibility is the main cost.** Alpha.6/core v3 accepts the observed 50-MiB create. Core v4 is required so v3 consumers fail closed at capability negotiation (`docs/mutation-contract.md:157-177`). Adding the limit to v3 also breaks the current adapter's exact `result.limits` validator (`src/adapter/core-probe.js:111-145`).
2. **One item bound is not a raw-input memory bound.** JSON whitespace and escape spelling can make a request arbitrarily larger than its decoded item. The current parser must buffer and parse it before candidate size is known. A finite raw-request cap is a second contract limit; claiming that 8 MiB alone solves input exhaustion would be false.
3. **Output amplification remains severe.** An 8-MiB item can yield about 19.6 MB before JSON overhead because mutation success returns decoded `body` plus base64 source. This exceeds the standard adapter's 1,048,576-byte stdout limit. The 50-MiB probe produced 122,334,911 output bytes. The semantic item limit improves this but does not align core and adapter limits.
4. **Legacy oversized items can become mutation-blocked.** Keeping validation and inspect permissive avoids bricking the ledger, but transition and unrelated patches must refuse until one patch shrinks the successor below the limit. Refusal precedence must be pinned against ledger-invalid, item-not-found, collision, revision, precondition, and claim-fence failures.
5. **Byte accounting is easy to get wrong.** Use serialized `Buffer.length`, not JavaScript string length, base64 character length, or body length. Tests need multi-byte UTF-8, exact 8,388,608, and 8,388,609-byte candidates.
6. **Live-consumer migration risk is currently low, not zero.** Read-only scan of `/Users/leestutzman/Documents/GitHub/PropertyCompass2/ledger` found exactly 1,574 items. Largest complete source is 80,676 bytes (item #1289); largest body is 33,357 bytes; p95 body is 10,197 and p99 is 20,688 bytes. Largest item is 0.96% of 8 MiB and largest body is 0.40%. No existing body is near the proposed bound. Direct edits or future generated decisions can still cross it.

## 4. Acceptance criteria

- Core capabilities emits exact `max_item_source_bytes: 8388608`; contract and adapter probes reject omission, renaming, type drift, or a changed value.
- For create, transition, patch body replacement, patch body append, and publish-claimed: an exact 8,388,608-byte successor reaches normal downstream handling; 8,388,609 bytes returns exact `item-source-too-large`, exit 2, `unchanged`, with exact domain-correct details.
- File and stdin mutation vectors agree. A 50-MiB create refuses and publishes no item. Every refusal leaves Markdown bytes unchanged and leaves no temporary or lock artifact.
- Invalid JSON and malformed/noncanonical base64 keep their existing `invalid-request` responses. The 11,534,336-byte publication transport boundary keeps exact boundary and boundary-plus-one tests. Size precedence is pinned against every earlier refusal class.
- A committed oversized legacy fixture still validates and inspects. A patch to at most 8 MiB succeeds; a patch, append, transition, or claimed publication whose successor remains larger refuses.
- Multi-byte UTF-8 fixtures prove source-byte accounting. Mutation guards remove each verb's check and change `>` to `>=`; focused tests must go red for each mutation.
- Core v3 and work-claim v1 consumers fail closed against the new negotiated versions. Adapter outcome validation accepts the new core and publication refusals only after the matching capability/version update.
- Normative mutation fixtures, envelope-domain fixtures, work-claim reference vectors, `test/work-claim-reference.js`, and `spec/adapter-reference.js` independently pin the value, refusal, state, and domain. Neither oracle is imported into `src/`.

## 5. Effort and blast radius

- Estimate: 3-5 focused engineering days for the semantic bound, dual-domain versioning, docs, exact fixtures, oracle changes, adapter updates, and release pins. Add 2-4 days if raw-input streaming or a second advertised request cap is in scope.
- Core touch points: shared limit definition, `src/cli.js`, `src/mutation.js`, `src/claim-publication.js`, capabilities, and error registries. Contract touch points: mutation, work-claim, adapter, and release notes.
- Conformance blast radius: core probe exact-member checks, adapter process-outcome error maps/details, work-claim reference model, envelope fixtures, mutation vectors, package/plugin metadata, and the shipped skill's alpha.6/core-v3 pins.
- Ledger blast radius: no schema migration and no rewrite if validation remains permissive. Operationally, only a future or legacy item above 8 MiB loses ordinary mutation access until shrunk.

## 6. Open questions for the maintainer

1. Confirm the limit is complete item source bytes, not body bytes. Body-only enforcement leaves decision and extension growth open and does not match publish-claimed.
2. Is one new refusal name a hard requirement? If yes, approve core contract 4 and work-claim API 2. If work-claim API 1 must remain byte-exact, publish-claimed must keep its misleading `invalid-request`, and the proposal cannot honestly promise one named refusal.
3. Is raw JSON exhaustion in scope? If yes, approve a second advertised `max_mutation_request_bytes` or a streaming parser. One semantic item limit cannot bound arbitrary JSON spelling.
4. Should a legacy oversized item permit only a one-step shrink to at most 8 MiB, or any strictly size-decreasing patch? The former is simpler and recommended; the latter needs a documented exception at every candidate check.
5. Is 8 MiB acceptable despite the adapter's 1-MiB stdout ceiling, or should response-size redesign become a prerequisite? Lowering the item limit enough to fit current success envelopes would be a second, much stronger narrowing of publish-claimed.
