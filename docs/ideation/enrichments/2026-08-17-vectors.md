## 1. The real gap

At `cd4b27d4fe5a051366ef6d5ba45223366d86b031`, the implementation runner discovers 15 case directories and 200 assertions through `runImplementationVectors` (`spec/run-adapter-implementation.js:970-1072`). It really spawns `adapters/<target>/entrypoint.js` over stdin/stdout (`spawnAdapterEntrypoint`, lines 114-183; `callShippedEntrypoint`, lines 186-230), and `core-baseline` first spawns `bin/wowbagger.js` and then invokes that entrypoint (`evaluateCoreBaselineAssertion`, lines 425-490).

The real-core coverage is broader than “case 10”: cases 03 `ready`, 04 `validate` failure, and 10 `capabilities` are all `equivalence`/`core-baseline` cases (`spec/fixtures/adapters/03-ready-forwarding/manifest.json:16-24`, `04-validation-failure-forwarding/manifest.json:15-23`, `10-capabilities-forwarding/manifest.json:16-29`). With no runtime config, the production entrypoint probes and launches the real core (`src/adapter/entrypoint-main.js:285-308,355-373`). No existing equivalence case invokes `inspect`, `create`, `transition`, or `patch`.

Case 11 is not end to end: each `process-outcome` assertion reads a hand-built process observation and directly calls production `mapProcessOutcome` (`spec/run-adapter-implementation.js:665-684`); it spawns neither adapter nor core. Case 07 sends only the missing-approval refusal through the entrypoint; its positive authority assertion directly calls `verifyMutationAuthority` (`spec/run-adapter-implementation.js:824-862`).

The test layer does not close that gap. `test/adapter-bootstrap-wire.test.js:24-60` crosses the real process wire, but its real-core cases are only `capabilities` and `ready` (lines 214-258). `test/adapter-invoke.test.js:134-223` proves exact approved-patch argv/stdin while injecting a timeout observation. `test/adapter-fence-refusal.test.js:174-219` proves synthetic fence envelopes. Conversely, the core-only mutation suite does run exact mutation inputs against isolated ledgers (`test/mutation-vectors.test.js:14-53`) but does not include the adapter.

Therefore the precise gap is: no conformance assertion, and no bootstrap-wire unit test, carries a valid trusted approval through a spawned adapter entrypoint, launches the real core with mutation stdin, validates the real core envelope, preserves its exact streams in the outer adapter result, and checks the resulting ledger state. There is also no real-core `inspect` refusal through the entrypoint.

History audit changes the motivation:

- The inspect defect is confirmed by `CHANGELOG.md:246-254` and fix commit `643ff88664b143e4776021b9715b6ef24e449b66` (2026-08-16). The mapper first landed in `9f37aa0ffb472d50ff981b29640fa1482776e860` (2026-08-09), so “for months” is contradicted by this repository; it existed for about a week and across tagged alphas, not months.
- The widened date refusal is confirmed (`CHANGELOG.md:362-372`), but commit `2b7e1603354e3d5ff3f5b0690ea65bfafd00a9e9` introduced the core shape, both adapter engines, case-11 vectors, and tests together. No committed or tagged interval here supports calling it a shipped adapter defect. It remains a valuable regression class.
- The documented second shipped adapter defect is instead namespace-first claim-fence dispatch: real unchanged refusals became `mutation-outcome-unknown` (`CHANGELOG.md:391-409`).

Resize the proposal to “end-to-end core-outcome vectors”: keep the mutation focus, but add one `inspect item-not-found` vector if the inspect regression claim is part of acceptance. Calling a mutation-only set proof against the inspect defect would be false.

## 2. Sharpened design

Add one equivalence case, tentatively `16-core-outcome-e2e`, with nine isolated `core-baseline` scenario assertions:

1. `inspect` / `item-not-found` from `spec/fixtures/mutations/inspect/manifest-not-found.json:1-42`.
2. `create` / committed, using the fixed caller ULID and bytes in `spec/fixtures/mutations/create/manifest-stdin.json:1-35` and `request.json:1-15`.
3. `transition` / committed from `spec/fixtures/mutations/transition-success/manifest.json:1-42`.
4. `patch` / committed body replacement from `spec/fixtures/mutations/patch-body/manifest.json:1-42`.
5. `patch` / committed declared extension replacement from `spec/fixtures/mutations/patch-extensions/manifest.json:1-52`.
6. `transition` / unchanged six-member date refusal from `spec/fixtures/mutations/date-rollback/expected.json:1-31`.
7. `create` / unchanged `claimed-item-write-refused`.
8. `patch` / unchanged `active-claim-write-refused`.
9. Any mutation / unchanged `claim-store-unavailable`, induced before mutation with a deterministic malformed `.git` marker.

“Publish-claimed refusals” must be renamed in the proposal. `publish-claimed` is not an adapter command (`CORE_COMMAND_ORDER`, `src/adapter/core-probe.js:6-8`). What the adapter consumes are the three `ledger-mutation` claim-fence refusal classes produced by legacy `create`/`transition`/`patch` (`docs/adapter-contract.md:674-729`). The real set should cover all three unchanged classes; retain synthetic case 11 for transition-vs-patch permutations and genuine `state: "unknown"`, whose real induction requires a fault/crash seam.

Fixture format should extend the existing `core-baseline` assertion with a `scenario`/subdirectory, not create a parallel runner protocol. Each scenario contains hashed `core-invocation.json`, `invocation.json`, mutation input, complete ledger-before/after bytes, `expected-core-stdout.jsonl`, and `expected-adapter-result.json`; Git scenarios also contain a fixed namespace and journal seed. `manifest.json` remains `adapter_vector_version: 1`, `mode: "equivalence"`, includes `direct-core`, and lists every byte in `artifacts`, preserving the current hash and fail-closed rules (`spec/fixtures/adapters/README.md:8-16,58-104`). Add explicit `derived_from` paths and SHA-256 values for reused mutation-fixture bytes, and fail if the local copies diverge; updating either side then requires a reviewed golden change.

For every assertion, materialize two independent temp workspaces from the same before snapshot: one for the direct-core baseline and one for the adapter. Reusing one workspace would make the baseline mutation alter the adapter precondition. Compare direct stdout to the committed bytes, the decoded adapter stdout to the same bytes, the whole outer adapter result to its committed expectation, and each workspace to the exact after snapshot. This generalizes `evaluateCoreBaselineAssertion` rather than using a `process_observation` override.

Approval is a prerequisite, not fixture decoration. Every mutation is gated in `invokeAdapter` (`src/adapter/invoke.js:206-250`), and the digest binds the exact absolute temp paths, argv, stdin, limits, instruction digest, executable identity, request ID, and adapter/core versions (`docs/adapter-contract.md:539-607`). Yet `runAdapterEntrypoint` currently passes none of `approval`, `now`, `redeemed_nonces`, or `core_executable_identity` to `invokeAdapter` (`src/adapter/entrypoint-main.js:355-373`) while advertising approval support (lines 41-79). A mutation through the shipped entrypoint can currently only reach `consumer-approval-required`.

Introduce a host-only runtime dependency/provider at the production entrypoint boundary, then let `spec/adapter-conformance-entrypoint-main.js` supply a consumer approval, pinned `now`, fresh nonce set, and the actual core executable digest. Do not add approval to the bootstrap request: that is model-controlled and violates `docs/adapter-contract.md:524-532,586-591`. The conformance wrapper must omit `coreProbe` when not overridden so the production default still probes the real core, and must omit `launch`/`process_observation` so the production launcher runs. The approval digest may be constructed from the independent oracle canonicalizer (`spec/adapter-reference.js:237-242`) after the temp root is known; it is test input, never expected output. If no real host approval provider is added, label the evidence honestly as “production adapter engine under a conformance host,” not live-consumer end to end.

Determinism must use fixed inputs, not output normalization:

- ULID: `create` accepts the caller-supplied ID, so commit a fixed valid ULID as existing vectors do; do not run `mint-id`. Its embedded timestamp fixes `created`. Exact request provenance fixes its timestamp.
- Revisions and item numbers: seed exact Markdown/config bytes; commit their SHA-256 revisions in requests; run create against an isolated empty schema-2 ledger so its number is 1. The existing mutation runner already proves this pattern (`test/mutation-vectors.test.js:20-49,76-123`).
- Dates: use literal request/item dates and the existing date-rollback bytes. Never replace dates in observed output.
- Claim refusals: initialize a temp Git repository with forced LF/autocrlf settings, a fixed `.wowbagger/namespace`, and a hand-authored claim journal. Seed a future clock floor and an active claim at fixed instants. `advanceClockFloor` returns `max(physicalNow,floor)` (`src/claim-operations.js:6-10`), and the legacy fence emits that effective value (`src/claim-coordinator.js:34-57,178-197`), so `observed_at` and the exact refusal bytes stay fixed without mocking the core clock. Add a fail-fast horizon assertion that wall time is before the seeded expiry. The journal will append a real-time `now`, but that untracked coordinator record is not in the adapter result; assert its allowed append shape separately and byte-compare the ledger itself.
- Outer bytes: hand-author the canonical one-object-plus-LF core stdout; mechanically derive only base64, byte length, and SHA-256 from those committed bytes, per the transport contract (`docs/adapter-contract.md:638-653`). No redaction or normalization step is permitted.

## 3. The tautology boundary

Bright-line rule: implementation code may execute a vector, but may never define its expected semantics.

May supply or mechanically generate:

- scenario selection and goldens authored from `docs/adapter-contract.md`, the independent oracle in `spec/adapter-reference.js`, and already normative `spec/fixtures/mutations/**` expected/source bytes;
- base64, SHA-256, and byte length of an already hand-authored expected byte string;
- temp absolute paths, two copied sandboxes, Git plumbing, a nonce, executable digest, and an approval digest needed to make the input valid;
- an oracle result as an additional differential assertion, provided it cannot overwrite or refresh the committed golden.

Must be hand-authored and reviewed as fixture data: exact mutation stdin, ledger pre/post bytes, core exit/stdout/stderr, adapter result, refusal code/state/details, fixed IDs/dates/revisions, scenario choice, and assertion IDs. Goldens must remain legible files with manifest hashes.

Forbidden: importing `src/adapter/process-outcome.js`, `src/adapter/invoke.js`, core serializers/validators, or current core output to create or update an expectation; recording a passing run as a golden; auto-refreshing fixtures; or masking unstable fields. A source helper may verify a committed expectation but cannot produce it. This prevents the same faulty guard or serializer from writing both sides of the assertion.

## 4. Hidden risks

1. Blocking — trusted approval is advertised but not plumbed by the spawned entrypoint. A conformance-only provider tests engine wiring, not a live consumer approval mechanism; conflating those claims would preserve the product gap.
2. High — real claim setup can become nondeterministic through wall time, random namespace, Git reconciliation, or a shared common directory. Fixed namespace/journal/future floor, isolated repositories, and a horizon failure are required; no normalization fallback.
3. High — correlated oracle drift. The date change modified core, both engines, and fixtures in one commit. Required deliberate-mutant proofs are stronger than a green differential alone.
4. Medium — runtime growth. Each implementation `core-baseline` assertion starts a direct core, an adapter process, the adapter's live core probe, and its invoked core; nine assertions add about 27 core starts plus nine adapter starts, before Git setup [INFERRED]. Keep one small case, isolate scenarios, measure current-vs-new wall time on both required Node runtimes, and do not migrate the 35 synthetic outcome cases.
5. Medium — cross-platform variance: temp path syntax enters approval digests; Git availability/config, CRLF conversion, executable discovery, process containment, and file identity differ. Keep paths out of expected output, force Git config and exact bytes, use `TMPDIR=/tmp`, and report platform evidence separately. Current fixtures already require a real checkout for case 10 (`spec/fixtures/adapters/README.md:24-56`).
6. Medium — duplicated core fixtures can drift. Pinned `derived_from` hashes should turn drift into an intentional review, not silently regenerate adapter goldens.
7. Low — the contract prose is stale around patch: the command table and approval text name only create/transition (`docs/adapter-contract.md:494-527`), while version 2 and code include patch (`docs/adapter-contract.md:1321-1339`; `src/adapter/invoke.js:17-18,125-134`). Resolve the prose before treating it as the sole authoring source.

## 5. Acceptance criteria

- The runner reports the existing 15/200 plus one nine-assertion case (16/209 if nothing else changes) [INFERRED], and both `spec/run-adapter-vectors.js` and `spec/run-adapter-implementation.js` consume every hashed artifact and fail closed on missing/extra/changed fixture data.
- All nine assertions run the direct real core and, separately, the spawned shipped entrypoint with a live core probe and real core launch. A child-process audit proves no `process_observation`, fake executable, or injected mutation result was used.
- Every mutation carries a valid consumer approval bound to its actual temp paths and exact bytes. Existing case 07 remains the companion negative: the same class of request without approval is `consumer-approval-required` and observes no core mutation launch.
- Success vectors match exact core exit/stdout/stderr, exact decoded adapter streams and stream hashes/lengths, and exact ledger post-state. Refusal vectors match exact nonzero exits and unchanged ledger bytes; claim-fence refusals arrive as `ok: true` adapter transport results, not adapter errors.
- Determinism is demonstrated by two consecutive full runs on the current Node and Node 20 commands required by `AGENTS.md`, with byte-identical reported expectations; Git cases use isolated common directories and leave no shared state.
- Inspect regression proof: temporarily restore the pre-`643ff88` unconditional canonical-mutation precondition in `validCoreErrorDetails` (`src/adapter/process-outcome.js:863-879`). The new real `inspect item-not-found` assertion must fail, observing `core-protocol-error`; restore the mutant and it passes.
- Date-shape regression proof: temporarily reduce `issueMembers` to the old four members (`src/adapter/process-outcome.js:950-984`). The real date-rollback assertion must fail as `mutation-outcome-unknown`; restore it and the exact six-member refusal is forwarded. This proves the requested class even though Git history does not prove it shipped broken.
- Actual shipped fence regression proof: temporarily remove namespace-first ledger-mutation dispatch. At least the real active-claim vector must fail as `mutation-outcome-unknown`; restoring dispatch makes all three real unchanged refusal classes forward exactly.
- No committed mutant, generated golden, repository write outside the intended implementation, or relaxation of the existing synthetic cases is accepted. Runtime deltas and platform skips are reported, not hidden behind overall exit 0.

## 6. Effort and blast radius

Estimate: medium, roughly 3–5 focused engineering days including negative-control demonstrations and two-runtime verification [INFERRED]. This is not fixture-only because trusted approval must cross the spawned entrypoint boundary.

Expected touch points: `spec/run-adapter-implementation.js`, `spec/run-adapter-vectors.js`, `spec/adapter-conformance-entrypoint-main.js`, narrowly `src/adapter/entrypoint-main.js` for host runtime plumbing, `spec/fixtures/adapters/README.md`, one new fixture subtree, and targeted runner tests. `docs/adapter-contract.md` needs the patch/approval correction and an evidence-status update. No core mutation semantics or oracle response guards should change.

Blast radius is medium: most work is conformance-only, but the entrypoint runtime signature is a security boundary and must default to no approval. The fixture addition increases normal verification time and adds Git-backed temp repositories. Production behavior should remain unchanged until a genuine trusted host provider is deliberately wired.
