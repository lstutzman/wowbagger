## 1. Dist-tag policy

- Live registry state on 2026-08-17 is `latest=0.1.0-alpha.1` and `next=0.1.0-alpha.6`
  (`npm view wowbagger dist-tags --json`). Bare `npm install wowbagger` therefore selects obsolete bytes. npm defines bare install as `latest` and recommends other tags for unstable releases
  ([npm dist-tag](https://docs.npmjs.com/cli/v11/commands/npm-dist-tag/)).
- Decision: while every release is `0.1.0-alpha.*`, delete `latest`; keep exactly `next=<newest published alpha>`. Bare install then fails loudly and `@next` is explicit prerelease consent. README already uses `@next`
  (`README.md:23-26,55-58,245-249,319-320`); add one version-free sentence that
  bare install is intentionally unsupported until stable.
- Rejected: point `latest` at `next`. It fixes staleness but makes npm's default channel silently unstable. Rejected: leave alpha.1 plus a README warning. Install resolution happens before the warning can protect a user.
- Encode policy in `scripts/release-channels.js`, exposed as `npm run release:channels -- check|repair <version>`. `check` requires `next=<version>` plus absent `latest`. `repair` is idempotent:
  add/move `next` only when needed and remove `latest` only when present. Every
  prerelease publish must use `npm publish --tag next`; plain `npm publish`
  would recreate/move `latest`.
- Deprecate only `wowbagger@0.1.0-alpha.1`, with a message naming `@next` and the exact skill/core pairing requirement. It remains installable and warns on later installs; this does not alter an existing installation, upgrade the stated live consumer, or notify it now
  ([npm deprecation](https://docs.npmjs.com/deprecating-and-undeprecating-packages-or-package-versions/)).
  Contact or migrate that consumer separately. Do not unpublish alpha.1.

## 2. The cut command

- Put logic in testable `scripts/cut-release.js`; expose `npm run release:cut -- <version> --date YYYY-MM-DD`. Do not put multi-file logic in a `package.json` shell string.
- Step 1, preflight: require a clean checkout; an explicit valid next SemVer; exactly one non-empty `## Unreleased`; no local tag, remote tag, or npm version
  for the target; and the current version at every declared release site.
  Require the final checkout that will receive the tag. Any mismatch exits
  before a write. [INFERRED] Requiring an explicit date avoids midnight and
  locale-dependent changelog output.
- Step 2, plan in memory: update `package.json:3`; both lockfile fields
  (`package-lock.json:3,9`); `.claude-plugin/plugin.json:4`;
  `.claude-plugin/marketplace.json:8,16,19`; every current-release README ref;
  both exact skill-pin mentions (`skills/wowbagger/SKILL.md:23-29`); and the
  changelog. Replace `## Unreleased` with a fresh empty `## Unreleased` followed
  by `## <version> - <date>`, so released notes move under the version while a
  future bucket remains. The last cuts, `310a9cc` and `5ebd40c`, prove this file
  set and also prove that `package-lock.json` cannot be omitted.
- Step 3, verify the plan before materialization: validate all JSON, exact match counts, allowed changed-file set, and release-site coverage described in
  section 4. Any failure discards the plan without touching the checkout.
- Step 4, materialize all planned bytes, then run the release gate with `TMPDIR=/tmp`: the full test suite on current Node and Node 20; adapter
  implementation vectors for `claude-code`, `codex`, and `opencode`; ledger
  validation; `npm audit --omit=dev`; and both Git diff checks. This matches
  `docs/adapter-release-path.md:49-67` and `README.md:841-857`. On red, restore
  the exact captured bytes, verify the original clean state, create no commit or
  tag, and exit nonzero.
- Step 5, stage only the allowed files, assert the staged file set again, and create one `Cut <version>` commit. Commit failure restores the pre-cut bytes
  if HEAD did not move. Then create `v<version>` at that commit. Tag failure
  leaves a clean, complete cut commit and exits nonzero; rerun verifies that
  commit and resumes tag creation. It never rewinds an existing commit.
- Step 6, after the tag exists, run `node scripts/verify-release-tag.js`. Order is mandatory: it resolves `refs/tags/v<package version>`, compares it
  with HEAD, and requires a clean tree (`scripts/verify-release-tag.js:12-33`).
  If this final check fails, remove only the newly created local tag when it
  still points at this command's commit; retain the complete commit for an
  inspectable, idempotent retry.
- Idempotency: target already cut, tag at clean HEAD, and all checks green exits 0 as `already cut`. A complete cut commit without its tag resumes at tagging.
  Any mixed metadata, different tag target, or published target version fails;
  it is never silently repaired.
- `--dry-run` executes the same planner, coverage checks, and gate against a temporary copy, prints the exact diff, commit subject, and tag, then proves
  repository HEAD, index, worktree, and refs are byte-for-byte unchanged. It
  does not use a separate lightweight code path.
- [INFERRED] “Atomic” can mean one internally consistent local commit, not one transaction across files, Git refs, a remote, and npm. The command stops at a
  verified local tag. Push commit and tag, then prove the remote tag resolves to
  that HEAD before publication. `npm publish --tag next` stays manual in an
  interactive PTY because the account uses a Chrome WebAuthn passkey and npm
  publication is irreversible. The one-time `latest` removal and alpha.1
  deprecation are also authenticated registry writes. Run the read-only channel
  check after publish.

## 3. Hidden risks — ranked

1. **Wrong tag target.** `v0.1.0-alpha.5` and `.6` point at merge commits
   `115799e` and `26369ef`, not cut commits `310a9cc` and `5ebd40c`. Tagging in a
   release worktree and then merging makes published HEAD differ from the tag,
   which the prepublish guard rejects. One-command cutting requires execution
   on the final branch tip, or the workflow must remain two-phase.
2. **Unknown version-ref sites.** Current tests cover named JSON fields, Git-ref patterns, and one skill sentence, not all semantic references
   (`test/packaging.test.js:44-66,176-182`). A newly added current-version line
   can survive a cut unless independent coverage discovery fails closed.
3. **False atomicity.** A green local cut cannot roll back a pushed Git tag or npm publication. Keep cut, push, publish, and registry verification as named
   states. Never report “released” after only the local command.
4. **Changelog misfiling.** Both recent cuts renamed `Unreleased` instead of recreating it; current `CHANGELOG.md:8` has no Unreleased section although
   `README.md:355-356` tells users to read one. Future changes can land under an
   already published release.
5. **Channel regression.** One accidental `npm publish` without `--tag next` restores `latest`. `prepublishOnly` cannot see the operator's publish flag;
   it only validates the local tag and checkout (`package.json:52`). Registry
   post-verification is mandatory.
6. **Guard overstatement.** `verify-release-tag.js` checks four plugin metadata values plus tag/HEAD/cleanliness, but not README, lockfile, changelog, or
   every skill pin. The full packaging test and coverage inventory must remain
   part of the cut gate; `prepublishOnly` alone is insufficient.

## 4. Acceptance criteria

- A checked-in `scripts/release-version-sites.json` classifies every literal occurrence of the current package version as `mutable` or `retained`, using
  JSON Pointers or anchored text locators with exact occurrence counts. The cut
  command never edits this manifest automatically.
- Before planning, scan every Git-tracked text file for the literal old version.
  Each occurrence must match exactly one manifest locator. After planning, old
  version occurrences must equal only the exact retained set (for example, the
  historical changelog header), and new version occurrences must equal the
  planned mutable set plus the new changelog header. Global grep-zero is wrong
  because history must retain old versions; exact-set equality is the proof.
- A test adds a new tracked fixture containing the old version without adding a manifest locator and proves both dry-run and real planning refuse it. Tests
  also prove duplicate, missing, and over-broad locators fail. This catches the
  “site added next month” drift class. [INFERRED] No grep can prove a semantic
  version reference that contains no old-version token; this explicitly defines
  the proof boundary.
- Successful plan updates package and lock versions, all four plugin identity values, every README current-release ref, both skill pin occurrences, and the
  changelog structure. `test/packaging.test.js:176-182` continues to prove the
  fail-closed required-version sentence; a new inventory test proves no second
  stale occurrence remains.
- Dirty checkout, invalid/non-increasing version, empty or duplicate Unreleased, existing target on npm, local/remote tag conflict, injected gate failure, and
  changed allowed-file set each exit nonzero with no tag and no partial bytes.
- Dry-run leaves HEAD, index, worktree hashes, and refs unchanged. Two real runs
  converge: the second reports `already cut`; an untagged complete cut resumes
  safely; a tag at another commit refuses.
- After cut, `scripts/verify-release-tag.js` passes only at clean tagged HEAD.
  Its existing dirty-byte test remains (`test/packaging.test.js:207-248`), and
  new tests cover absent and wrong-target tags.
- Registry acceptance is exact: prerelease state is `{next: <published>}` with
  no `latest`; alpha.1 carries the approved warning; bare install fails; explicit
  `wowbagger@next` resolves to the new version. These are post-publish checks,
  not claims made by the local cut.

## 5. Effort and blast radius

- Effort: medium, about 1–2 engineer days. Most work is failure-path and idempotency tests, not string replacement. Full release-gate runtime remains
  the operator cost on every cut and dry-run.
- Repository blast radius: release tooling/tests, `package.json` script entry, release-path documentation, README channel wording, and a release-site
  manifest. No `src/`, contract, adapter, oracle, or ledger behavior changes.
- Operational blast radius: high but narrow. Dist-tag repair changes all future bare npm installs; deprecation affects alpha.1 install output; tag and npm
  publication are public and immutable. Existing installed alpha.1 bytes keep
  running.

## 6. Open questions for the maintainer

1. Approve absent `latest` until first stable release, or intentionally accept
   prerelease-by-default and point `latest` at `next`?
2. May the cut command commit and tag directly on final `main`, or must cuts keep
   the current worktree-then-merge topology? The latter cannot be one command
   because the final tag target does not exist until after merge.
3. Should tags remain lightweight, matching alpha.5/.6, or become annotated or
   signed? Should Git push remain an explicit step or be a separate ship command?
4. Must every release have non-empty Unreleased notes, and is explicit
   `--date` acceptable?
5. Approve the alpha.1 deprecation text and separate contact plan for the live
   consumer. When stable ships, should `next` be removed or retained for the
   next prerelease line?
