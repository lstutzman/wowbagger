## 1. Sharpened design

Both premises were re-verified. `readGitHeadLedger` enumerates every HEAD blob below the ledger, filters to Markdown outside the root `.wowbagger/`, and batch-reads the contents of every match; batching reduces processes but not bytes read (`src/git-reconciliation.js`, `readGitHeadLedger` and `readBlobBatch`). `publishClaimedCandidate` computes `lockIds` from every item in the loaded ledger, and `acquireLocks` performs one exclusive create, metadata write, and fsync for each unique ID (`src/mutation.js`, `publishClaimedCandidate`, `mutateExistingItem`, and `acquireLocks`). Thus a valid 1,500-item fixture causes 1,500 item-lock acquisitions. The repository benchmark does not time the lock phase separately, so the claim that it is the dominant wall cost is not verified by checked-in evidence (`bench/mutation-latency.bench.js`, `run`, `measurePublish`, and report construction).

### Stage 1: make the MAY-encode rule a two-tier identity index

- Contract: within the recursively traversed ledger, excluding root `.wowbagger/`, a Markdown basename exactly `<canonical-id>.md` claims that ID. Its frontmatter ID MUST equal the basename ID. A mismatch is a deterministic ledger-validation error, proposed as `filename-id-mismatch`; it must never fall through to another file. A non-conforming basename remains legal and obtains its identity from frontmatter. Two conventional paths claiming the same ID fail closed as an ambiguity/duplicate, rather than winning by traversal order.
- Lookup: change `readGitHeadLedger` to accept the exact requested ID set. Run one `git ls-tree` name scan over the whole ledger. Batch-read conventional candidates for those IDs. Only when at least one requested ID lacks such a candidate, batch-read and parse every non-conforming Markdown blob once, satisfying all misses in that pass. Do not parse unrelated conforming blobs. Return explicit not-found results plus the HEAD commit; retain no cross-call cache. The unavoidable cost becomes `O(tree names + requested conventional bytes + fallback bytes)`, not `O(all item bytes)` [INFERRED].
- The tree search MUST NOT be restricted to `layout.items_directory`. Layout is write-path authority, while readers deliberately traverse the complete ledger and report items outside layout (`SPEC.md`, sections 3 and 4.1; `src/ledger.js`, `loadLedger` and `collectMarkdownFiles`). A misplaced `<id>.md` must therefore still be found at HEAD and then remain invalid for layout reasons. Current tests require a misplaced journaled item to leave claim reconciliation consistent while reporting invalid ledger validation (`test/misplaced-item-layout.test.js`, “misplaced journaled item” and “layout introduced after journaled item” tests).
- Create behavior remains `items_directory/<id>.md`; collision checks may now use the basename contract but must preserve the existing refusal at the final derived path (`docs/mutation-contract.md`, section 7; `src/mutation.js`, `createItem` path derivation). The current prose saying IDs MUST NOT be inferred from filenames must be replaced, not qualified ambiguously (`SPEC.md`, section 4.1; `docs/mutation-contract.md`, section 7).
- The reconciliation caller must derive its requested set before reading HEAD: every item ever named by a `publish-finalization` or `legacy-mutation` entry, plus any successful `publish-final` lacking finalization (`src/git-reconciliation.js`, `coordinatedItems`; `src/claim-publication.js`, `reconcileClaimJournal`). This preserves behavior, but means the fast path is proportional to historical coordinated cardinality `C`; after every item has been coordinated, `C = N` [INFERRED].

### Stage 2: replace publish item-lock closure with the existing namespace process lock

- Do not introduce a timed lease. `publish-claimed` already runs under `withClaimLock` from replay through intent fsync, mutation, and terminal append (`src/claim-publication.js`, `publishClaimed`; `src/claim-store.js`, `withClaimLock`). Provisioned legacy create/transition/patch also enter the same namespace lock (`src/claim-coordinator.js`, `withLegacyMutationFence`). Its owner is recoverable only when the OS reports the PID absent, never by elapsed time (`docs/work-claim-contract.md`, section 6; `src/claim-store.js`, `acquireClaimLock`). That existing lock is the single coarse acquisition.
- Add an internal “namespace lock held” mutation strategy. In that strategy, `publishClaimedCandidate` acquires zero `.wowbagger-locks/<id>.lock` files, but keeps the fresh complete working-tree reload and all candidate/revision/validation checks. Ordinary create/transition/patch retain the current per-ID closure and bounded reread/retry protocol (`docs/mutation-contract.md`, section 6; `src/mutation.js`, `mutateExistingItem`). Because namespace ownership is stable rather than item-set-dependent, publish no longer widens or retries a lock closure.
- Remove the callable unlocked seam: make `publishClaimedCandidate` private or require an internal, unforgeable namespace-lock capability. It is currently imported directly by a mutation-guard test (`test/large-ledger-mutation-guard.test.js`, publish test), which would otherwise become a lock-free public path.
- Preserve per-item candidate objects, journal records, refusals, operation IDs, revisions, envelopes, and ordering byte-for-byte for equivalent semantic and journal/ledger fault schedules. Define this parity boundary to exclude injected failures in the removed per-item lock I/O; those failures cannot remain observable after their I/O is removed [INFERRED].
- Crash recovery is unchanged: a successor first recovers the dead process lock, then resolves an intent by comparing actual, expected, candidate, and higher-epoch revisions; an indeterminate state remains `publication-outcome-unknown` (`src/claim-publication.js`, `reconcileClaimJournal`; `docs/work-claim-contract.md`, section 6). Tests must cover death before mutation, after rename but before `publish-final`, and after `publish-final` but before finalization/HEAD reconciliation.

### Stage 3: make the cache a measured decision, not an implementation commitment

- Extend the 1,500-item benchmark with deterministic phase counters: complete loads, HEAD tree entries, HEAD blobs/bytes read, namespace-lock acquisitions, and item-lock creates/fsyncs. Add phase wall times around lock acquisition and HEAD reading. The current benchmark reports operation wall time and load-count reliability but cannot attribute the result (`bench/mutation-latency.bench.js`, `trackedLoadLedger`, `measureGitHeadLedger`, and `buildReliability`).
- Measure both the current in-process module path and a fresh-process CLI path. The fixture currently uses conforming root `<id>.md` names and direct module calls for mutation/publication, which can exaggerate the value of a process-local cache (`bench/ledger-fixture.js`, item creation loop; `bench/mutation-latency.bench.js`, `measureCreate`, `measureTransition`, and `measurePublish`).
- Record a cache decision only after the matrix in section 4. Any future cache must be disposable, derived from a complete observable snapshot, invalidated by direct edits, layout changes, Git HEAD changes, and worktree changes, and never become journal or identity authority [INFERRED].

## 2. Hidden risks

1. **Critical — mixed-version writers can violate serialization.** A new binary honoring only the namespace lock can race an older or unprovisioned binary honoring only item locks. The work-claim profile excludes hostile/direct writers, but cooperative-version compatibility still needs an explicit release boundary (`docs/work-claim-contract.md`, sections 1.1 and 6; `docs/mutation-contract.md`, section 6). Coarse locking is safe only after a quiesced all-writer upgrade, or behind a compatibility fence [INFERRED].
2. **High — layout-scoped lookup would corrupt reconciliation semantics.** Current readers include misplaced items and validation reports `item-outside-layout`; using `layout.items_directory/<id>.md` as the HEAD lookup would turn a layout error into a false missing/stale item (`src/ledger.js`, `loadLedger`; `test/misplaced-item-layout.test.js`, journal-consistency cases). Name lookup must scan the complete tree.
3. **High — historical coordination can erase Stage 1's payoff.** Reconciliation checks all `coordinatedItems`, not only the item in the current request (`src/git-reconciliation.js`, `coordinatedItems` and reconciliation loop). A long-lived 1,574-item ledger may converge on reading nearly every conforming blob even after the optimization [INFERRED]. Benchmark `C = 1` and `C = N`.
4. **High — the benchmark does not support the proposal's causal claim.** It counts complete loads and measures whole operations, but has no item-lock acquisition counter or phase timer (`bench/mutation-latency.bench.js`, measurement and reliability helpers). Reordering work on the stated “dominant” cause without instrumentation risks optimizing the wrong phase.
5. **High — crash equivalence is broader than ledger atomicity.** The namespace lock spans journal intent and terminal records as well as the rename (`src/claim-publication.js`, `publishClaimed`). Killing its owner half-published must leave `claim-verify` able to recover the lock and produce the same success, conflict, or unknown finding; a simple concurrent-success test is insufficient (`src/claim-publication.js`, `verifyClaimJournal` and pending-intent resolution).
6. **Medium — current publish lock metadata is internally inconsistent.** `lockSource` writes operation `publish-claimed`, while `validLockOwner` accepts only create/transition/patch; a concurrent observer can classify a live publish item lock as `invalid-shape` (`src/mutation.js`, `lockSource` and `validLockOwner`; `docs/mutation-contract.md`, section 6). This previously unnamed defect strengthens removal of publish item locks, but also makes “byte-identical under lock faults” impossible without defining scope.
7. **Medium — legal legacy names create a performance cliff.** One requested miss triggers the specified full scan of non-conforming blobs. Correctness is stable, but latency depends on filename distribution, so migrating only this repository does not prove consumer performance [INFERRED].
8. **Medium — rename migration can break human references without changing item bytes.** Checked-HEAD searches show repository documents/code refer to several human-named ledger paths [verified in `ledger/items/` references]. Leaving alias Markdown files would create duplicate items because every Markdown file is currently read as an item (`SPEC.md`, section 3; `src/ledger.js`, `collectMarkdownFiles`). References must move in the same commit.
9. **Medium — an in-process cache benchmark can be a false positive.** Ordinary CLI invocations start fresh processes, while the benchmark calls modules in one process (`bench/mutation-latency.bench.js`, mutation measurement functions). A cache decision without subprocess numbers may optimize only the harness [INFERRED].

## 3. Contract impact

- **Normative contracts:** update `SPEC.md` sections 3 and 4.1 for two-tier filename identity, traversal, mismatch, ambiguity, and fallback; update `docs/mutation-contract.md` sections 5–7 for validation, create collision/path behavior, the publish namespace-lock exception, and compatibility; update `docs/work-claim-contract.md` section 6 only to state that merge-coordinated publication relies on the already-held namespace lock and takes no item locks. Journal `item_path` remains diagnostic rather than path authority (`docs/work-claim-contract.md`, section 6, journal path rules).
- **Code surfaces:** `src/git-reconciliation.js` (`readGitHeadLedger`, target-set derivation, batch selection); `src/ledger.js` (filename/frontmatter validation); `src/mutation.js` (`publishClaimedCandidate`, `mutateExistingItem`, lock strategy, create collision); `src/claim-publication.js` and `src/claim-coordinator.js` (locked capability plumbing); `src/claim-store.js` only if lock ownership must be asserted; `bench/mutation-latency.bench.js` and `bench/ledger-fixture.js` (instrumentation/matrices).
- **Fixtures/tests/oracles:** add mixed-name, mismatch, duplicate conventional basename, fallback, layout-misplacement, `C = 1/C = N`, mixed-version refusal, and crash-barrier fixtures. Update adapter/core fixtures for the version. `spec/adapter-reference.js` moves only for the required core version and new validation contract. `test/work-claim-reference.js` and normative work-claim output fixtures must remain unchanged if byte parity is achieved; changing them is evidence of a work-claim contract change, not routine fixture maintenance.
- **Version domains:** bump core mutation contract 3 to 4. Promoting filename convention to validity/identity authority changes accepted ledgers and reconciliation results, so silently redefining published v3 is unsafe (`docs/mutation-contract.md`, section 1; `src/adapter/core-probe.js`, `CORE_CONTRACT_VERSION`). Keep item schema at 2 and layout at 1 because neither data shape changes (`SPEC.md`, sections 2–3). Keep work-claim API/envelope at 1 and adapter contract at 2 if request/result/journal/adapter shapes remain byte-identical; adapter manifests and fixtures still change their required core version (`docs/work-claim-contract.md`, section 3.1; `spec/adapter-reference.js`, contract constants).
- **This repository:** the checked-HEAD inventory under `ledger/items/` is 119 item files: 94 already `<id>.md` and 25 human-named; `ledger/.wowbagger/layout.json` selects `items`. In a quiesced migration, dry-run an exact old→`<frontmatter-id>.md` map; require a valid ledger, unique IDs, empty destinations, no live lock, and clean reference rewrite; rename without changing item bytes; update path references in the same Git commit; then run `validate` and `claim-verify`. Existing journal revisions need no rewrite because content is unchanged and journal paths are diagnostic [INFERRED]. The non-atomic migration safeguards in `docs/schema-2-migration.md` are the minimum operational model.
- **Live 1,574-item consumer:** the repository records that staging size, but not its filename distribution (`ledger/items/wb_01M07J8W5TS6PVKFZ1T4RTN184.md`, Context/Acceptance Criteria). Therefore Stage 1 must remain correct before migration. Inventory conforming, non-conforming, mismatch, occupied destination, and referenced paths first; upgrade every cooperative writer; then use a quiesced, reviewed rename-only commit and validate/`claim-verify` before resuming. If migration is deferred, fallback remains correct but its measured cost is accepted [INFERRED].

## 4. Correct staging

Do not accept the proposed order without an evidence slice. The checked-in benchmark cannot confirm that locks dominate. Use this order:

0. **Instrument and baseline.** On the same commit, runtime, hardware, and filesystem, measure reliable p50/p95 operation and phase times plus deterministic counters on 1,500 items. Gate: identify whether item-lock acquisition or HEAD blob reading is the largest attributable phase.
1. **Original Stage 2 first if the brief's dominance claim is confirmed.** Removing 1,500 create/write/fsync/unlink cycles is independent of filename policy and should precede the smaller cause. Gate: namespace acquisitions `= 1`, publish item-lock acquisitions `= 0`, complete loads remain `= 2`, crash/parity suite passes, and end-to-end improvement exceeds run noise. If HEAD reading is larger, retain original Stage 1 before Stage 2 instead.
2. **Original Stage 1.** Gate on deterministic HEAD counters and contract parity across all-conforming, one-miss, legacy-heavy, layout-configured/misplaced, `C = 1`, and `C = N` fixtures. The gate is blobs/bytes read, not merely fewer `git` processes.
3. **Original Stage 3.** Re-run module and fresh-process CLI measurements on current Node and Node 20. A derived-cache design may begin only if the maintainer's end-to-end SLO is still missed and repeated load/parse work is the largest remaining attributable phase [INFERRED]. Otherwise record “no cache.”

This conditional reorder separates an unverified performance claim from the two independent correctness changes; neither optimization is allowed to borrow the other's benchmark gain.

## 5. Acceptance criteria

### Stage 1

- A mutation guard proves that requesting one conventional ID reads one matching blob after the tree scan and no unrelated conforming blob; changing the implementation back to “read all” fails the test.
- Multi-ID lookup, absent ID, one and many non-conforming fallbacks, filename/frontmatter mismatch, two conventional paths, and conforming-plus-legacy duplicate all have deterministic results independent of traversal order.
- A misplaced `<id>.md` remains discoverable at HEAD; the claim journal stays consistent while `ledger_validation` reports the same outside-layout error required today (`test/misplaced-item-layout.test.js`, journal-consistency cases).
- Create still targets `layout.items_directory/<id>.md`, refuses occupied destinations, and never treats layout as the read boundary (`docs/mutation-contract.md`, section 7).
- Before/after migration inventories prove the same ID set and byte-for-byte item contents/revisions, zero human-named items, no broken repository path references, and passing `validate` plus `claim-verify`.
- Benchmark guards assert tree-entry, blob, and byte counts for all-conforming/legacy-heavy and `C = 1/C = N`; a fast-path implementation that merely hides reads behind `cat-file --batch` fails.

### Stage 2

- On a valid 1,500-item publish, counters prove exactly one namespace-lock acquisition and zero item-lock creates/writes/fsyncs/unlinks. Create/transition/patch retain their existing per-ID lock-closure counts and retry behavior.
- Injecting a duplicate ID, dangling relation, or target revision change between the first snapshot and the retained reload still refuses without changing the target. Removing that reload makes the guard fail (`src/mutation.js`, `mutateExistingItem` post-lock reload).
- Concurrent provisioned legacy mutation receives the same locked refusal/envelope; the approved mixed-version boundary is tested rather than assumed (`src/claim-coordinator.js`, `withLegacyMutationFence`).
- Kill-point tests at pre-intent, post-intent/pre-rename, post-rename/pre-terminal, and post-terminal/pre-finalization prove successor recovery and exact `claim-verify` findings (`src/claim-publication.js`, `publishClaimed`, `reconcileClaimJournal`, and `verifyClaimJournal`).
- Success, fence refusal, ledger revision conflict, validation refusal, idempotent replay, and indeterminate publication preserve exact per-item journal/envelope bytes. Any excluded obsolete item-lock fault is named explicitly.
- No exported or directly test-callable candidate function can enter the zero-item-lock strategy without verified namespace ownership.

### Stage 3

- The benchmark publishes raw samples, p50/p95, reliability verdict, and deterministic phase counters for current Node and Node 20, module and fresh-process CLI, all-conforming/mixed names, and `C = 1/C = N`.
- Results are compared on the same immutable commit and environment; any unreliable series is reported as inconclusive, matching the benchmark's existing reliability principle (`bench/mutation-latency.bench.js`, `buildReliability`).
- The decision record states the maintainer-approved latency SLO and residual dominant phase. Meeting it closes the cache decision as “do not build”; missing it permits a separately designed cache, not automatic implementation.

## 6. Effort and blast radius

- **Stage 1 — L.** Git reconciliation, complete-ledger validation, create collision/path rules, layout interaction, core version negotiation, adapter manifests/oracle fixtures, repository migration, consumer migration, documentation, and benchmark fixtures. The algorithm is moderate; contract/version and two-ledger migration make the blast radius large.
- **Stage 2 — L (M code, L assurance).** Mutation locking, claim coordinator/publication/store boundary, journal crash recovery, concurrency and fault injection, mutation guards, mixed-binary release operations, and contract prose. Once the compatibility policy is approved, production code is localized; proving crash and byte parity is not.
- **Stage 3 — M.** Benchmark harness, subprocess runner, phase instrumentation, fixture matrices, Node-version runs, and a decision record. This rating excludes implementing a cache; a cache would be a new separately sized design.

## 7. Open questions for the maintainer

1. Must filename authority be mandatory core contract v4, as recommended, or an opt-in mapping/layout capability? Published core v3 cannot safely acquire new validity semantics silently.
2. May the release require a quiesced, all-writer upgrade and declare older item-lock-only binaries non-cooperative, or must the new core provide a dual-lock/compatibility fence? This determines whether Stage 2 can deliver the lock reduction.
3. What end-to-end p50/p95 SLO, on which consumer hardware/filesystem and command mix, gates the cache decision? “Faster” is not a decision threshold.
4. Is the 1,574-item consumer migration an upgrade prerequisite or a later optimization supported indefinitely by fallback? That choice sets the operational window and the acceptable legacy performance cliff.
